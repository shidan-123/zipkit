# 维护指南

> 面向"这个仓库归我管"的人。目标是：**每周花 10 分钟，仓库一年不烂。**

---

## 一、日常节奏表

| 频率 | 干什么 | 耗时 |
|---|---|---|
| 每次改代码 | 跑 `pytest`，全绿再 commit | 1 分钟 |
| 每周 | 看一次 Issues / 有没有人提 PR | 5 分钟 |
| 每月 | `pip list --outdated` 看依赖；跑一次全量测试 | 10 分钟 |
| 每季度 | 更新路线图；检查安全公告 | 30 分钟 |
| 每年 | 更新 `LICENSE` 年份；评估要不要继续维护 | 10 分钟 |

## 二、开发环境从零搭起来

```bash
git clone https://github.com/shidan-123/zipkit.git
cd zipkit

python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -e ".[dev]"            # 装上 7z 支持 + 测试依赖
pytest -q                          # 应该全绿（55 passed）
```

> `.venv/` 已在 `.gitignore` 里，不会被提交。

### 常用命令

```bash
pytest -q                                   # 全部测试
pytest tests/test_safety.py -v              # 只跑安全测试
pytest -k "7z" -v                           # 只跑 7z 相关
python scripts/make_demo.py demo            # 重新生成样例
python -m zipkit web --no-browser           # 本地起服务调试
```

## 三、发版清单（照着做，不会漏）

### 1. 确认干净

```bash
git status                 # 不该有未提交改动
pytest -q                  # 全绿
```

### 2. 改版本号（**三处要一致**）

| 文件 | 位置 |
|---|---|
| `pyproject.toml` | `version = "1.0.1"` |
| `zipkit/__init__.py` | `__version__ = "1.0.1"` |
| `CHANGELOG.md` | 新增一节 |

> 版本号建议遵循语义化：修 bug 改末位（1.0.**1**）、加功能改中位（1.**1**.0）、不兼容改首位（**2**.0.0）。

### 3. 写 CHANGELOG

按「新增 / 修复 / 变更 / 安全」四类写，每条说"用户能感知到什么"，别写"重构了 xxx"。

### 4. 提交与打标签

```bash
git add -A
git commit -m "release: v1.0.1"
git tag -a v1.0.1 -m "v1.0.1"
git push origin main
git push origin v1.0.1
```

### 5. 在 GitHub 上发布 Release

网页 → Releases → Draft a new release → 选标签 → 粘贴 CHANGELOG 那一节 → Publish。

## 四、依赖怎么升

只有两个依赖会出现：

| 依赖 | 作用 | 什么时候必须升 |
|---|---|---|
| `py7zr`（可选） | 解 7z | 官方发安全补丁时 |
| `pytest`（开发） | 跑测试 | 跟随大版本即可 |

### 升级流程

```bash
pip install --upgrade py7zr
pytest -q                        # 全绿才能改 pyproject.toml
# 然后手动把 pyproject.toml 里的 py7zr>=0.20 改成新下限
```

**原则**：不要用 `>=` 卡死最新版；`py7zr>=0.20` 这种"最低支持版本"写法对用户最友好。

### 安全公告

订阅这几个源，出高危漏洞时及时发补丁版：

- Python 官方安全公告：<https://python.org/news/security/>
- CVE 搜索关键词：`python zipfile`、`tarfile`、`zip slip`
- GitHub 会自动给依赖发 Dependabot 提醒（仓库 Settings → Code security 打开）

## 五、数据备份（别把唯一副本放在 GitHub）

GitHub 可能因为各种原因访问不了。建议三层：

| 层 | 做法 | 恢复速度 |
|---|---|---|
| 1 | GitHub 仓库本身 | 秒级 |
| 2 | 本地 `git clone` 一份 | 分钟级 |
| 3 | 每月打包一次推到网盘/移动硬盘：`git bundle create zipkit-2026-10.bundle --all` | 小时级 |

`git bundle` 是单文件备份，能完整还原整个仓库历史：

```bash
git clone zipkit-2026-10.bundle 恢复出来的仓库
```

## 六、Issue 怎么处理

### 打标签

| 标签 | 用途 |
|---|---|
| `bug` | 功能不符合预期 |
| `enhancement` | 新功能请求 |
| `question` | 用法疑问（能转成文档就更新 FAQ） |
| `security` | 安全问题（**优先，且不要在公开 Issue 里贴利用细节**） |
| `good first issue` | 留给新贡献者 |

### 处理顺序

1. **安全问题** → 当天响应，私信沟通，修完再公开
2. **能复现的 bug** → 先写一个失败的测试，再修（防止回归）
3. **功能请求** → 对照路线图回答"在计划里 / 暂不考虑 + 原因"
4. **用法疑问** → 回答后，把答案补进 `docs/故障排查.md`

### 回复模板

```markdown
感谢反馈！我需要确认几个信息才能定位：

1. 操作系统 + Python 版本（`python3 --version`）
2. 完整命令
3. 完整报错（从 ❌ 开始那几行）
4. 是每次都能复现，还是偶发？

另外，`python3 -m zipkit check 你的文件` 的输出也很有帮助。
```

## 七、必须守住的三条底线

### ① 安全测试不许删

`tests/test_safety.py` 里的用例对应的都是真实攻击手法（路径穿越、压缩炸弹）。哪怕重构，这些断言也必须保留。

### ② 默认行为不许变"危险"

- 默认**不覆盖**同名文件
- 默认**不跟随**符号链接
- 默认**只监听** 127.0.0.1

任何"为了方便"而放宽默认值的 PR，都要在 CHANGELOG 的「变更」里显著标注。

### ③ 错误信息必须带"怎么办"

`ZipKitError(message, hint)` 里 `hint` 不能为空。用户看到报错时，必须有下一步动作。

## 八、出事了怎么回滚

### 情况 1：刚发的版有严重 bug

```bash
# 本地回退到上个版本，重新打补丁版
git revert <出问题的提交>
# 或者
git checkout v1.0.0 && git switch -c hotfix/1.0.2
```

在 GitHub Releases 里把坏版本标记为 **Pre-release** 或直接删除，避免用户下载。

### 情况 2：误删了分支/提交

```bash
git reflog                 # 找到丢失的提交
git checkout -b 恢复 <那个 commit>
```

`reflog` 默认保留 90 天，基本都能救回来。

### 情况 3：把敏感信息提交了（密码、token）

1. **立刻**去对应平台作废那个凭据（最重要，比改仓库紧急）
2. `git filter-repo --path 泄露文件 --invert-paths` 清历史
3. 强推：`git push --force-with-lease`
4. 通知所有 fork 过的人（他们本地还有旧历史）

> 预防：提交前跑 `git diff --cached`，或装 `gitleaks` 做 pre-commit 检查。

## 九、什么时候该停止维护

诚实地说，个人项目都有寿命。出现以下情况时，在 README 顶部加一段 **Unmaintained** 说明，比放着不管更负责：

- 连续 6 个月没有提交
- 有已知安全问题但你没时间修
- 上游依赖（如 `py7zr`）已停止维护

说明里至少写清楚：**当前状态、替代方案、最后可用版本**。
