# 微信小程序方案（v2.0 规划）

> 先说结论：**v1.0 不做小程序，是有意为之，不是漏了。**
> 这篇文档说明"为什么"和"真要做时怎么做"。

---

## 一、为什么不能"把桌面版搬进小程序"

微信小程序不是"能跑 JS 的浏览器"，它有一套完全不同的约束：

| 约束 | 具体规定 | 对本项目意味着什么 |
|---|---|---|
| **包体积** | 主包 ≤ 2 MB；分包后总包 ≤ 20 MB | 7z 解压的 WASM 版约 2~5 MB，塞不进主包；只能放分包，且首次使用要下载 |
| **运行环境** | 只有 JS 逻辑层 + `WXWebAssembly`（受限 WASM） | 没有 Python、没有系统 `unzip`、没有 `zlib` 之外的解压库 |
| **WASM 限制** | 内存上限、不支持部分系统调用、不能多线程 | 大文件解压容易 OOM；7z 的固实压缩包基本无解 |
| **文件来源** | 只能用 `wx.chooseMessageFile()` 从**聊天记录**选，或沙箱文件 | 无法"从电脑拖一个 2 GB 的日志压缩包进来" |
| **文件写入** | `wx.getFileSystemManager()` 写沙箱，10 MB 临时文件有上限 | 解压结果不能直接落到用户"下载文件夹" |
| **网络** | 必须 HTTPS + **已备案域名**，且需在后台配置白名单 | 一旦走云端，就必须有服务器、域名、备案 |
| **审核** | 涉及"文件处理"需要说明用途，可能被要求资质 | 上线周期不可控 |

**一句话**：桌面版的核心能力（任意大小、任意格式、本地处理）在小程序里都做不到。

---

## 二、三条可行路线对比

### 路线 A：纯前端 WASM（不推荐）

把 `zip.js` / `7z-wasm` 塞进分包，全在手机本地解压。

| 维度 | 评价 |
|---|---|
| 优点 | 无需服务器，隐私最好，零运营成本 |
| 缺点 | 包大（2~5 MB 分包）、内存吃紧（解 200 MB 就崩）、7z 支持几乎不可用、iOS/Android 表现不一致 |
| 能做什么 | 只能解 **zip/gz 且 ≤ 20 MB**，压缩只能打 zip |
| 工作量 | 2~3 周（含真机适配） |

**结论**：功能退化到"能看不能用"，用户会失望。

---

### 路线 B：云端 API（推荐，但要花钱）

小程序只做"选文件 → 上传 → 显示结果"，解压/压缩全在服务器上跑——**直接复用本项目的 `core/` 代码**。

```text
小程序                          服务器（Python）
┌──────────────┐   HTTPS   ┌─────────────────────────┐
│ chooseMessage│ ────────▶ │ FastAPI / Flask          │
│ File()       │           │   ├─ core.compress.pack  │
│ 显示结果      │ ◀──────── │   ├─ core.extract.extract│
│ 下载/转发     │           │   └─ core.office.extract │
└──────────────┘           │ (临时文件 60s 后删除)     │
                           └─────────────────────────┘
```

| 维度 | 评价 |
|---|---|
| 优点 | 功能与桌面版**完全一致**；小程序端代码量很小（300 行内） |
| 缺点 | 需要服务器 + 域名 + 备案；有流量成本；用户文件经服务器中转（需明确隐私政策） |
| 能做什么 | 全部功能，包括 7z、Office 读文 |
| 工作量 | 2 周后端 + 1 周小程序 + 2~4 周备案 |

**成本估算**（小规模）：

| 项目 | 费用 |
|---|---|
| 云服务器（1 核 2G，够用） | 约 ¥60~100/月 |
| 域名 | 约 ¥30~60/年 |
| ICP 备案 | 免费，但需 2~4 周，且要实名 |
| 小程序认证 | 个人主体免费（功能受限），企业 ¥300/年 |

---

### 路线 C：混合（长期最优，但复杂）

小文件走 WASM 本地解压，大文件走云端 API。

**结论**：v2 后期再考虑，前期没必要。

## 三、如果做，MVP 长什么样

### 范围（刻意砍到最小）

| 做 | 不做 |
|---|---|
| 解压 `.zip` / `.gz` / `.7z` | 不做压缩（手机端压缩需求很低） |
| 单文件 ≤ 50 MB（服务端限制） | 不做批量 |
| 结果显示文件名 + 大小，可"保存到手机"/"转发给朋友" | 不做预览、不做在线编辑 |
| 服务端 60 秒后自动删除临时文件 | 不做用户系统、不做历史记录 |

### 技术要点

```js
// 1. 从聊天记录选文件（唯一入口）
wx.chooseMessageFile({
  count: 1,
  type: 'file',
  extension: ['zip', '7z', 'gz'],
  success: (res) => {
    const file = res.tempFiles[0];   // 有 path 和 size
    uploadFile(file.path);
  }
});

// 2. 上传（必须 HTTPS + 备案域名 + 后台配置 uploadFile 合法域名）
wx.uploadFile({
  url: 'https://api.example.com/unpack',
  filePath: file.path,
  name: 'file',
  success: (res) => {
    const data = JSON.parse(res.data);
    // 3. 写回沙箱，再让用户"保存到手机"
  }
});

// 4. 保存
wx.getFileSystemManager().saveFile({ tempFilePath, success: ... });
```

### 服务端要点（复用现有代码）

```python
from zipkit.core.extract import extract
from zipkit.core.safety import Limits

@app.post("/unpack")
async def unpack(file: UploadFile):
    with tempfile.TemporaryDirectory() as tmp:
        src = Path(tmp) / "in.zip"
        src.write_bytes(await file.read())
        # 关键：每请求单独限流，且总量远小于桌面版
        report = extract(src, dest=Path(tmp) / "out", limits=Limits(max_total=200 * 1024**2))
        return zip_dir(Path(tmp) / "out")
```

**必须补的三件事**（桌面版不需要）：

1. **请求限流**：按 IP / 用户限速，否则一人就能打满服务器
2. **自动清理**：临时文件 60 秒后删除（定时任务）
3. **隐私政策**：明确"文件仅用于解压，X 秒后删除，不落盘、不分析"

## 四、我的建议

```text
现在（v1.0）   ✅ 桌面版跑通，积累 Star 和 Issue
   ↓ 3~6 个月
v1.2          ✅ PyInstaller 打包，Windows 用户双击即用（比小程序更能扩大用户量）
   ↓ 有人明确要求"手机上用"时
v2.0          ⚠️ 再评估要不要做小程序
```

**判断标准**（满足两条再动手）：

1. 桌面版有 ≥ 100 Star 或有真实用户反馈"手机上也需要"
2. 你愿意承担每月 ¥100 的服务器成本 + 一次 2~4 周的备案流程

**如果只是想"有个小程序作品写进简历"**，那更该做的是：
用路线 A 做一个**只支持 zip 的极简版**（1~2 周），把省下的时间花在 README 和演示上——
招聘方看的是"你能不能把一件事讲清楚"，不是一个功能残缺的工具。

## 五、风险清单

| 风险 | 可能性 | 应对 |
|---|---|---|
| 备案被卡 | 中 | 用已有备案域名；或先做"仅自己可用"的体验版 |
| 审核不通过（文件处理类） | 中 | 明确写"格式转换工具"，不提供云存储 |
| 服务器被刷 | 高 | 限流 + 单文件 50 MB + 每日配额 |
| 用户传敏感文件 | 中 | 隐私政策 + 60 秒删除 + 不记录日志内容 |
| 小程序框架变更 | 低 | 后端 API 保持稳定，前端可替换 |

---

## 六、结论

- **v1.0 交付桌面三平台**（已完成，见 [README](../README.md)）
- **小程序放到 v2.0**，走路线 B（云端 API 复用 `core/`）
- 现在需要的准备：把 `web/server.py` 的接口设计当成"未来 API 的雏形"，保持参数语义一致

这条路线的好处是：**桌面版每一行 core 代码，将来小程序都能直接复用**，不会白写。
