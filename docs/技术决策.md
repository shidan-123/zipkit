# 技术决策记录（ADR）

> 记录"为什么这么做"，以及**我改掉了你原需求里的哪三处**。
> 以后想改设计时，先读这篇，避免把踩过的坑再踩一次。

---

## 一、需求复核：三处必须纠正的地方

你的原话是：

> 对 `.txt .log .csv .json .bmp .wav .tiff` 进行压缩，对 `.zip .7z .gz .docx .xlsx .pptx` 进行解压；Linux/Windows/macOS 可安装使用，也可微信小程序使用。

### 纠正 ①：「解压 docx/xlsx/pptx」对普通用户没有意义

**技术事实**：这三种文件本身就是 ZIP 容器（OOXML 标准），里面是：

```
document.docx
├── [Content_Types].xml      ← 类型清单
├── _rels/.rels              ← 关系表
├── word/document.xml        ← 正文（一堆 XML 标签）
├── word/styles.xml
└── word/media/image1.png
```

**问题不在"能不能解"，而在"解了之后你拿它干嘛"**：

1. 解开看到的是 `<w:p><w:r><w:t>你好</w:t></w:r></w:p>` 这种 XML，不是文字；
2. 改完再压回去，由于 `[Content_Types]`、校验和、关系 ID 对不上，**文档大概率打不开**；
3. 真要"看内容"，直接用 Office 打开就行，比解包快一百倍。

**改成了什么**：把「解压 Office」降级为"研究用途"（真的能解，会提示你解开的是 XML），
主推 **`zipkit text`：直接抽出纯文字**——这才是用户真正想做的事。

**如果要保留原需求**：`unpack 报告.docx` 依然可用，只是会看到一条提醒。

---

### 纠正 ②：「微信小程序版」不是加个前端，是换一套架构

微信小程序有三条绕不过去的限制：

| 限制 | 具体数值/表现 | 对本项目的影响 |
|---|---|---|
| 包体 | 主包 ≤ 2 MB，总包 ≤ 20 MB | 塞不下 7z/zip 的原生库；WASM 版本也要 2~5 MB，且要与 UI 分包 |
| 运行环境 | 无本地进程，只有 JS + 受限 WASM（`WXWebAssembly`） | 不能用系统 `unzip`、不能调用 Python |
| 文件来源 | 只能通过 `wx.chooseMessageFile` 从聊天记录选，或 `wx.getFileSystemManager` 读沙箱 | 无法"拖一个 3 GB 的日志文件进来" |

**结论**：小程序只能做**功能子集**，而且必须有服务端。三种路线见 [小程序方案](小程序方案.md)，
我的建议是 **v2.0 再做**，用「云函数解压 + 小程序只做上传/下载」。

**改成了什么**：v1.0 交付三平台桌面版（含本地网页界面），小程序作为独立里程碑，先写方案不写代码。

---

### 纠正 ③：`bmp / wav / tiff` 用 ZIP 压缩，收益远低于你的预期

| 格式 | 内部结构 | ZIP 实际收益（实测） | 真正该用的 |
|---|---|---|---|
| `.bmp` | 未压缩的像素点阵 | **7.2%** | PNG（无损，通常小 5~10 倍） |
| `.tiff` | 常已 LZW 压缩 | **5.8%** | PNG / WebP |
| `.wav` | PCM 波形 | 10%~40%（合成音可到 98%） | FLAC（无损，约省一半） |
| `.docx` | 已 DEFLATE | 6.7% | 不用压 |
| `.xlsx` | 已 DEFLATE | 11.3% | 不用压 |

**这不是 bug，是信息论**：DEFLATE 对"已经接近随机"的数据无能为力。

**改成了什么**：

1. 压缩**照做**（你要求的功能都在），但结果里会照实显示每个文件的收益；
2. 收益 < 15% 时主动提示"这不是故障，换格式才有效"；
3. 新增 `zipkit check`——**压缩前先体检**，避免白忙一场。

## 二、架构选型：为什么是「Python + 本地网页」

需求是"三平台都能装、界面简单"。可选方案：

| 方案 | 安装包大小 | 三平台一致性 | 开发成本 | 新手友好 | 结论 |
|---|---|---|---|---|---|
| Electron + JS | ~150 MB | 好 | 中 | 好 | ❌ 为一个压缩工具装 150 MB 不合理 |
| Tauri + Rust | ~10 MB | 好 | **高**（要 Rust 工具链） | 好 | ❌ 门槛对"想改代码的人"太高 |
| PyQt / Tkinter | ~40 MB | 中（Linux 缺 Qt 库） | 中 | 一般 | ❌ 界面丑、跨平台坑多 |
| **Python + 本地网页** | **0 MB**（有 Python 即可） | **完全一致**（同一套 HTML） | **低** | **好** | ✅ **选它** |
| 纯命令行 | 0 | 好 | 最低 | 差 | ✅ 作为补充 |

**关键洞察**：用户要的是"简单界面"，不是"原生界面"。浏览器是每台电脑都有的、免费的、跨平台的 GUI 运行时。
用 `http.server` 起一个只监听 `127.0.0.1` 的服务，就同时得到了：

- 零安装（有 Python 就行）
- 真正的跨平台（同一份 HTML 在三个系统渲染一致）
- 拖拽上传、进度反馈这些 Web 原生能力
- 后续做小程序时，**后端 API 可以直接复用**（`web/server.py` 的接口设计就是按"未来给小程序调用"留的）

### 代价（诚实记录）

- 需要用户机器上有 Python（v1.2 计划用 PyInstaller 打包成双击即用的单文件，消除这个前提）
- 网页版上传走 Base64，比原生多 33% 内存开销，所以默认上限 64 MB
- 浏览器不能"写任意路径"，所以解压结果是再打一个 zip 让用户下载（多一步）

## 三、为什么只用标准库

| 依赖 | 用途 | 为什么不用第三方 |
|---|---|---|
| `zipfile` | 压缩 / 解 zip | 标准库；`compresslevel` 3.7+ 就够用 |
| `tarfile` | tar / tar.gz | 标准库 |
| `gzip` | .gz | 标准库 |
| `http.server` | 网页服务 | 标准库；Flask/FastAPI 对"本机单用户"是过度设计 |
| `xml.etree` | 解析 docx/xlsx/pptx | 标准库；`lxml` 需要编译，会拖累安装 |
| `py7zr` | 7z | **唯一例外**：7z 算法复杂，标准库没有。做成可选依赖，没装时给出明确提示 |

**收益**：`pip install zipkit-tool` 在离线环境也能装；不会因为某个依赖弃坑而整个项目挂掉；
安全审计面小得多。

## 四、安全模型（分层防御）

解压工具天生是攻击面。设计上假设"每个压缩包都是恶意的"：

### 第 1 层：入口白名单

打开前先看**文件头魔数**（`PK\x03\x04`、`7z\xbc\xaf\x27\x1c`、`\x1f\x8b`），
不看扩展名——防止有人把恶意文件改名为 `.txt.zip`。

### 第 2 层：成员名合法性

拒绝以下成员名（`core/safety.py::validate_member`）：

- 绝对路径 `/etc/passwd`
- Windows 盘符 `C:\Windows\...`
- UNC 路径 `\\server\share`
- 任何 `..`（含 `a/../../b`、`..\..\b`）
- 控制字符（伪造扩展名）
- Windows 设备名（`CON`、`NUL`、`COM1`…）

**关键设计**：先**全部校验完**再开始写盘。任何一个成员不合法 → 整个包拒绝，不留半成品。

### 第 3 层：资源上限

| 限制 | 默认值 | 防的是 |
|---|---|---|
| 成员数 | 20,000 | inode 耗尽攻击 |
| 解压总量 | 2 GB | 磁盘写满 |
| 单文件 | 1 GB | 单个大文件撑爆 |
| 压缩比 | 200:1 | **压缩炸弹**（42 KB 解出 5 TB 的那种） |
| 流式计数 | 边写边数 | 头部 `file_size` 撒谎 |

### 第 4 层：写入行为

- 默认不覆盖，自动 `名字 (1).ext`
- 失败自动删除半截文件（否则用户会拿到"看起来正常"的损坏文件）
- tar 里的 symlink / 硬链接 / 设备文件一律跳过

### 第 5 层：网页服务

- 只绑定 `127.0.0.1`（`--host` 默认值，文档里明确警告别改）
- 每次启动随机 token，POST 必须带 `X-ZipKit-Token`（防别的网页偷偷调本机接口）
- `Content-Length` 上限校验（防一个请求打满内存）
- 响应头 `X-Content-Type-Options: nosniff`

### 已知未覆盖的威胁（诚实清单）

| 威胁 | 现状 | 计划 |
|---|---|---|
| 加密 ZIP | 直接报错，不支持 | v1.1 |
| RAR / 分卷压缩 | 不支持 | 不在计划内（专利/复杂度） |
| ZIP 里的畸形路径（超长、NUL） | 依赖 Python 解压后校验 | 持续观察 |
| 解压后**打开**恶意文件（如 `.exe`） | 不检测 | 不做（超出工具职责） |

## 五、已知限制

| 限制 | 原因 | 规避方式 |
|---|---|---|
| 网页版 ≤ 64 MB | Base64 + 内存 | 用命令行 |
| 不支持 `.rar` | 专利与复杂度 | 先转 `.zip` |
| 不支持加密包 | 未实现 | 系统工具先解 |
| Windows 上无 GUI 安装包 | v1.0 范围 | `python -m zipkit web` |
| `.xlsx` 只导数值，不含公式计算结果差异 | 只读 `<v>` 缓存值 | 用 Excel 另存为 csv |
| 极老的 ZIP（GBK 编码无标记）可能乱码 | 编码探测有限 | Windows 用 7-Zip 手动指定 GBK |

## 六、如果重来一次，会改什么

1. **把 `pack` 的"目录输入"默认扁平化**——现在会带一层目录名，虽然安全但新手会疑惑。
2. **`web` 界面直接用 `<dialog>` 做结果弹窗**——现在的内联卡片在长文件名下会撑宽。
3. **CLI 加 `--dry-run`**——现在只能靠 `check` 估，不能真的"模拟压缩"。
4. **测试里加属性测试（hypothesis）**——随机生成压缩包成员名，能覆盖更多畸形输入。
